# Triage

Triage decides what kind of attention a request needs. It does not describe implementation progress. An implementation ticket's `Execution` state belongs to `to-tickets` and `implement-spec`; triage only records readiness and category.

Read `docs/agents/issue-tracker.md` and `docs/agents/triage-labels.md` before tracker work. If either is absent, stop and direct the user to `/skill:setup-matt-pocock-skills`. Read [AGENT-BRIEF.md](AGENT-BRIEF.md) and [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) when their workflows apply. Use the configured read-only tracker commands for inspection and the configured write commands only when the maintainer has authorized that class of external mutation.

## Roles and state

Every triaged request has exactly one category role (`bug` or `enhancement`) and one triage state role (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`). The configured label mapping supplies the actual strings. Do not use implementation states such as `open`, `claimed`, or `complete` as triage labels.

For an external pull request, treat the attached diff as the request surface. `ready-for-agent` means a durable brief describes the remaining work; `ready-for-human` means implementation or merge judgment remains with a person. Include only external PRs in discovery when the tracker configuration says PRs are in scope; an explicitly named PR is always eligible for inspection.

Every remote comment or issue body written by this workflow starts with:

```text
> *This was generated by AI during triage.*
```

## Discovery

With no specific request, query the configured tracker and show counts plus oldest-first summaries for:

1. unlabeled issues or requests;
2. items in `needs-triage`;
3. `needs-info` items with reporter activity since the last triage note.

Tag external requests as `[PR]` or `[issue]` where applicable. Let the maintainer choose what to inspect. Do not change labels while merely showing the queue.

## Specific request

1. Read the full issue or PR, including comments, labels, author, dates, and for a PR its diff. Read prior triage notes so settled answers are not asked again.
2. Read the project context, relevant ADRs, and the configured tracker instructions. Search the codebase by domain concept for an existing implementation and report the search scope. Read every `.out-of-scope/*.md` record and surface a relevant prior rejection.
3. Recommend one category and one state with concrete reasoning. For bugs, reproduce the reporter's path where practical. For PRs, inspect the actual diff and run the relevant checks. Report `confirmed`, `failed`, or `insufficient detail`; do not call a partial check end-to-end evidence. Do not claim runtime validated without executing the actual runtime path; upstream triage is not yet runtime validated in Pi.
4. If requirements remain unclear, use the Pi-native interview: read `~/.pi/agent/skills/grilling/SKILL.md` and `~/.pi/agent/skills/domain-modeling/SKILL.md`, then present each frontier round with `question` or `questionnaire`. The TUI is preferred; use numbered Markdown only when interactive UI is unavailable. Do not answer HITL questions for the maintainer. Record settled terms and decisions in the domain docs only under the existing authorization.
5. Present the proposed outcome and wait for maintainer direction before applying it, unless the maintainer gave a direct state override. A direct override skips grilling but still requires a brief when moving to an agent-ready state.
6. Apply the outcome through the configured tracker. For `ready-for-agent` and `ready-for-human`, post an [agent brief](AGENT-BRIEF.md). For `needs-info`, use specific questions and preserve established facts. For `wontfix`, distinguish already implemented from rejected enhancement; only rejected enhancements are recorded in `.out-of-scope/`.

Local Markdown writes update the issue file and append history under `## Comments`; remote writes use the configured CLI/API and the AI disclaimer above. Remote writes, label changes, assignment, comments, closure, and PR/MR state changes are separate authorization classes; reuse an authorization already granted for that class during this session and do not silently mirror local state remotely.

## Resume rules

On resumption, compare the last triage note with new reporter activity, preserve settled answers, and ask only outstanding questions. A triage state is not evidence that implementation has started or finished. Note that triage is ported for Pi workflows but not yet runtime validated in Pi; do not claim it has been runtime validated or end-to-end verified without executing the actual runtime path. Report what was inspected, what was verified, what was not run, and any pending human or external write.
